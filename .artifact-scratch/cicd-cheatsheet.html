Jak działa Twój pipeline CI/CD

Rozbiór na czynniki pierwsze plików, które razem budują i wystawiają frontend: main.yml, Dockerfile, docker-compose.yml + docker-compose.prod.yml — plus ocena podejścia i ściągawka na później.

Cały przepływ w jednym obrazku

    deploy -->|"SSH"| run
    hub -.->|"pull"| run
    run --> container

Lewy podgraf dzieje się na GitHubie (build), prawy — dopiero na Twoim serwerze (deploy i uruchomienie).

Kto za co odpowiada

Dockerfile build · GitHub

Przepis na obraz. Trzy etapy: deps instaluje zależności, builder odpala npm run build (z Next.js output: 'standalone'), runner kopiuje tylko gotowy build do czystego, małego obrazu node:22-alpine i uruchamia go jako user bez uprawnień roota. Nie zna serwera, nie zna Docker Hub — jego jedyne zadanie to zamienić kod źródłowy w gotowy, uruchamialny obraz.

main.yml → job build build · GitHub

Loguje się do Docker Hub sekretami z repo, każe Dockerowi zbudować obraz wg Dockerfile i wypycha go pod dwoma tagami: :latest oraz :<sha commita>. To jedyne miejsce, gdzie obraz faktycznie powstaje.

main.yml → job deploy most GitHub → serwer

Nie buduje niczego. Kopiuje aktualny docker-compose.prod.yml na VPS przez SCP, potem łączy się po SSH i każe serwerowi: zatrzymaj stary kontener, pull nowego obrazu z Docker Hub, up -d, posprzątaj. To jedyny fragment, który dotyka Twojego serwera.

docker-compose.yml runtime · tylko lokalnie

Wersja do dewelopmentu. Ma sekcję build:, więc docker-compose up --build zbuduje obraz z Twojego Dockerfile od zera i odpali go lokalnie — do sprawdzenia, czy produkcyjny obraz w ogóle wstaje, zanim cokolwiek trafi na serwer. Ten plik nigdy nie jedzie na VPS.

docker-compose.prod.yml runtime · serwer

Instrukcja uruchomienia kontenera na produkcji — porty (3002:3000), nazwa, zmienne środowiskowe, restart policy. Tylko sekcja image:, bez build: — serwer nie ma nawet możliwości zbudowania czegokolwiek, tylko pull gotowca z Docker Hub. Ten plik SCP kopiuje na VPS i on tam realnie żyje.

Plik po pliku, linijka po linijce

Komentarze wyleciały z Dockerfile i main.yml — całe wyjaśnienie jest tutaj, zawsze aktualne z tym, co faktycznie jest w repo.

#kodco robi
1FROM node:22.1.0-alpine AS depsStartowy obraz tego etapu: Node 22.1.0 na Alpine (mały, ok. 40MB). Etap nazwany deps — dalej można się do niego odwołać przez --from=deps.
2RUN apk add --no-cache libc6-compatDogrywa bibliotekę zgodności glibc — część paczek npm z natywnymi modułami jej potrzebuje, a Alpine ma domyślnie tylko musl libc.
3WORKDIR /appKolejne komendy w tym etapie odpalają się względem /app w obrazie (tworzy katalog, jeśli nie istnieje).
4COPY package*.json ./Kopiuje tylko package.json i lockfile — celowo bez reszty kodu, żeby Docker mógł cache'ować tę warstwę, dopóki zależności się nie zmienią.
5RUN npm ciInstaluje zależności dokładnie według lockfile — czysta, powtarzalna instalacja, szybsza niż npm install w CI.
7FROM node:22.1.0-alpine AS builderNowy etap od czystego obrazu, nazwany builder. To, co wyprodukował deps, trzeba jawnie skopiować.
8WORKDIR /appKatalog roboczy dla tego etapu.
9COPY --from=deps /app/node_modules ./node_modulesPrzenosi gotowy node_modules z etapu deps, zamiast instalować zależności po raz drugi.
10COPY . .Dopiero teraz kopiuje resztę repo do obrazu — to, czego nie wykluczył .dockerignore.
12ARG NEXT_PUBLIC_BASE_URLDeklaruje argument budowania — wartość trzeba podać z zewnątrz przez --build-arg (albo build-args: w workflow) w momencie docker build.
13ENV NEXT_PUBLIC_BASE_URL=$NEXT_PUBLIC_BASE_URLPrzepisuje ten argument na zmienną środowiskową — dopiero jako ENV widzi ją proces npm run build, który zaraz wypiecze ją do kodu JS.
15RUN npm run buildWłaściwy build Next.js. Tu NEXT_PUBLIC_BASE_URL trwale ląduje w bundlu JS wysyłanym do przeglądarki.
17FROM node:22.1.0-alpine AS runnerTrzeci, ostatni etap — od zera, bez śladu po node_modules czy kodzie źródłowym z poprzednich etapów. To on stanie się finalnym, wypychanym obrazem.
18WORKDIR /appKatalog roboczy obrazu produkcyjnego.
20ENV NODE_ENV productionNext.js i wiele bibliotek zachowuje się inaczej w trybie produkcyjnym: więcej optymalizacji, mniej ostrzeżeń dev.
22RUN addgroup --system --gid 1001 nodejsTworzy systemową grupę nodejs o stałym GID — potrzebna do uruchomienia kontenera bez roota.
23RUN adduser --system --uid 1001 nextjsTworzy systemowego użytkownika nextjs należącego do tej grupy — to on uruchomi aplikację.
25COPY --from=builder /app/public ./publicStatyczne pliki (obrazki, favicon) z etapu builder.
26COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./Samowystarczalny build Next.js (dzięki output: 'standalone') — własny minimalny server.js i tylko potrzebne zależności. --chown od razu ustawia właściciela na nowego użytkownika.
27COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/staticZasoby statyczne z builda (JS/CSS chunks) — standalone output ich automatycznie nie kopiuje, trzeba dorzucić osobno.
29USER nextjsOd tej linii kontener przestaje działać jako root — realne ograniczenie na wypadek włamania przez aplikację.
31EXPOSE 3000Dokumentacyjna deklaracja portu — sama go nie otwiera, to robi ports: w compose.
32ENV PORT 3000Standalone server Next.js czyta tę zmienną, żeby wiedzieć, na jakim porcie nasłuchiwać.
33ENV HOSTNAME "0.0.0.0"Każe serwerowi nasłuchiwać na wszystkich interfejsach kontenera, nie tylko localhost — inaczej nie byłby osiągalny z zewnątrz.
35CMD ["node", "server.js"]Komenda uruchamiana przy starcie kontenera: odpala serwer wygenerowany przez standalone build.

Co jest potrzebne gdzie

ElementLokalnie (dev)GitHub Actions (CI)Serwer (produkcja)
Dockerfile opcjonalnie — zwykle używasz npm run dev bez Dockera używany do zbudowania obrazu nieużywany bezpośrednio — obraz przychodzi już gotowy
docker-compose.yml sekcja build: pozwala zbudować i odpalić lokalnie (docker-compose up --build) — —
docker-compose.prod.yml — nieużywany do budowania, tylko kopiowany przez SCP na serwer sekcja image: mówi, co ściągnąć i uruchomić
Docker Hub — cel push źródło pull
Sekrety .env.local ewentualnie DOCKER_USER, DOCKER_PASSWORD, SSH_HOST, SSH_USER, SSH_KEY w GitHub → Settings → Secrets brak — serwer tylko wykonuje polecenia przysłane po SSH

Ocena podejścia

✓ Solidny fundament

Wzorzec „zbuduj na CI → wypchnij do rejestru → serwer tylko pulluje i odpala” to standard branżowy nawet w dużych firmach — dobrze, że serwer nigdy nie widzi kodu źródłowego ani nie buduje niczego lokalnie. Multi-stage Dockerfile z standalone Next.js i użytkownikiem bez roota to solidna, świadoma robota, nie przypadek. Do jednego VPS z jednym kontenerem — dokładnie tyle infrastruktury, ile potrzeba, bez nadmiarowego Kubernetesa czy własnego rejestru.

Ściągawka na później

Lokalnie — chcę zobaczyć produkcyjny obraz na własnym laptopie

# zbuduj lokalnie z Dockerfile i odpal wg docker-compose.yml
docker-compose up --build

# tylko zbuduj, bez odpalania
docker-compose build

# podejrzyj, czy zmienna build-time faktycznie wjechała do buildu
docker-compose build --build-arg NEXT_PUBLIC_BASE_URL=http://localhost:8080

GitHub Actions — co się dzieje po git push na master

# 1. job "build" na GitHubie
docker login ...
docker build -f Dockerfile --build-arg NEXT_PUBLIC_BASE_URL=... \
  -t sebastiankociuba/node-frontend:latest .
docker push sebastiankociuba/node-frontend:latest

# 2. job "deploy" — SCP-uje docker-compose.prod.yml, potem po SSH:
DC="docker compose"; sudo $DC version || DC="docker-compose"
sudo $DC -f docker-compose.prod.yml down || true
sudo $DC -f docker-compose.prod.yml pull
sudo $DC -f docker-compose.prod.yml up -d
docker image prune -f

Ręcznie na serwerze — debugowanie

# wejdź na VPS i sprawdź co żyje
ssh user@serwer
cd /var/www/frontend-node

docker ps                                          # czy kontener VPS-2-FE działa
docker logs -f VPS-2-FE                             # logi na żywo
docker compose -f docker-compose.prod.yml config    # jaki obraz/porty faktycznie zostaną użyte
docker compose -f docker-compose.prod.yml pull && \
docker compose -f docker-compose.prod.yml up -d     # ręczny redeploy bez CI

Kto tworzy obraz?

Wyłącznie GitHub Actions, wg przepisu z Dockerfile. Serwer nigdy nie buduje.

Kto uruchamia kontener?

Wyłącznie serwer, wg instrukcji z docker-compose.prod.yml. GitHub nigdy nie odpala kontenera produkcyjnego.
