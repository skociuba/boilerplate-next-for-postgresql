Jak działa Twój pipeline CI/CD

Rozbiór na czynniki pierwsze trzech plików, które razem budują i wystawiają frontend: main.yml, Dockerfile, docker-compose.yml — plus ocena podejścia i ściągawka na później.

Kto za co odpowiada

Dockerfile build · GitHub

Przepis na obraz. Trzy etapy: deps instaluje zależności, builder odpala npm run build (z Next.js output: 'standalone'), runner kopiuje tylko gotowy build do czystego, małego obrazu node:22-alpine i uruchamia go jako user bez uprawnień roota. Nie zna serwera, nie zna Docker Hub — jego jedyne zadanie to zamienić kod źródłowy w gotowy, uruchamialny obraz.

main.yml → job build build · GitHub

Loguje się do Docker Hub sekretami z repo, każe Dockerowi zbudować obraz wg Dockerfile i wypycha go pod dwoma tagami: :latest oraz :<sha commita>. To jedyne miejsce, gdzie obraz faktycznie powstaje.

main.yml → job deploy most GitHub → serwer

Nie buduje niczego. Kopiuje aktualny docker-compose.yml na VPS przez SCP, potem łączy się po SSH i każe serwerowi: zabij stare kontenery, pull nowego obrazu z Docker Hub, up -d, posprzątaj. To jedyny fragment, który dotyka Twojego serwera.

docker-compose.yml runtime · serwer (i lokalnie)

Instrukcja uruchomienia kontenera — porty (3002:3000), nazwa, zmienne środowiskowe, restart policy. Na serwerze wskazuje image:, więc docker-compose pull ściąga gotowca z Docker Hub. Ten sam plik ma też sekcję build:, więc lokalnie możesz nim zbudować obraz od zera zamiast go ściągać.

Co jest potrzebne gdzie

ElementLokalnie (dev)GitHub Actions (CI)Serwer (produkcja)
Dockerfile opcjonalnie — zwykle używasz npm run dev bez Dockera używany do zbudowania obrazu nieużywany bezpośrednio — obraz przychodzi już gotowy
docker-compose.yml sekcja build: pozwala zbudować i odpalić lokalnie (docker-compose up --build) nie jest używany do budowania, tylko kopiowany na serwer sekcja image: mówi, co ściągnąć i uruchomić
Docker Hub — cel push źródło pull
Sekrety .env.local ewentualnie DOCKER_USER, DOCKER_PASSWORD, SSH_HOST, SSH_USER, SSH_KEY w GitHub → Settings → Secrets brak — serwer tylko wykonuje polecenia przysłane po SSH

Ocena podejścia

✓ Solidny fundament

Wzorzec „zbuduj na CI → wypchnij do rejestru → serwer tylko pulluje i odpala” to standard branżowy nawet w dużych firmach — dobrze, że serwer nigdy nie widzi kodu źródłowego ani nie buduje niczego lokalnie. Multi-stage Dockerfile z standalone Next.js i użytkownikiem bez roota to solidna, świadoma robota, nie przypadek. Do jednego VPS z jednym kontenerem — dokładnie tyle infrastruktury, ile potrzeba, bez nadmiarowego Kubernetesa czy własnego rejestru.

Co warto poprawić

realny bugTrigger na gałąź „add,edit-delete” prawdopodobnie nie działa jak myślisz

branches: [add,edit-delete] w YAML to jeden string „add,edit-delete” z przecinkiem w nazwie, a nie dwie gałęzie. Deploy odpali się tylko wtedy, gdy naprawdę istnieje gałąź o tej dosłownej nazwie.

fix — jeśli chodziło o dwie gałęzie, zapisz je jako osobne pozycje listy: branches: [main] (albo [add, edit-delete] ze spacją, co YAML czyta jako dwa elementy).
realny bugNEXT_PUBLIC_BASE_URL nie dociera do obrazu budowanego na CI

Next.js wypieka zmienne NEXT_PUBLIC_* do kodu JS w momencie builda, nie przy starcie kontenera. Lokalnie docker-compose.yml przekazuje ją przez args:, ale job build w main.yml woła build-push-action bez żadnego build-args — więc obraz wypychany na Docker Hub ma tę zmienną pustą, niezależnie od tego, co ustawisz w environment: w compose. Ustawienie environment: BASE_URL=... w compose nie naprawia tego — to zmienna runtime, a front potrzebuje jej w buildzie.

fix — dodaj do kroku build-push-action w main.yml: build-args: NEXT_PUBLIC_BASE_URL=https://twojadomena.pl.
porządekZabijanie kontenerów po porcie 3002 przed docker-compose down jest zbędne

Linijka docker rm -f $(docker ps -aq --filter publish=3002) robi ręcznie to, co i tak zrobi docker-compose down zaraz potem — to podwójne zabezpieczenie, które ma sens tylko jeśli poza compose kiedyś ktoś odpalił kontener ręcznie na tym porcie.

fix — zostaw jako świadomy „bezpiecznik” albo usuń, jeśli masz pewność, że port 3002 zawsze należy do tego compose.
porządekdocker-compose (v1) zamiast docker compose (v2)

Binarka docker-compose z myślnikiem to stary, wycofywany plugin Pythona. Jeśli serwer ma nowszego Dockera, komenda docker compose (bez myślnika, jako subcommand) jest szybsza i aktywnie wspierana.

fix — sprawdź na serwerze docker compose version; jeśli działa, podmień komendy w skrypcie SSH.
porządekJeden plik compose do dev i do prod

Nie jest to błąd — docker-compose pull ignoruje sekcję build:, więc na serwerze i tak leci gotowy obraz. Ale trzymanie build: i image: w jednym pliku, który wysyłasz na produkcję, bywa mylące przy czytaniu za pół roku.

fix — opcjonalnie rozdziel na docker-compose.yml (dev, z build:) i docker-compose.prod.yml (tylko image:), i SCP-uj na serwer tylko ten drugi.

Ściągawka na później

Lokalnie — chcę zobaczyć produkcyjny obraz na własnym laptopie

# zbuduj lokalnie z Dockerfile i odpal wg docker-compose.yml
docker-compose up --build

# tylko zbuduj, bez odpalania
docker-compose build

# podejrzyj, czy zmienna build-time faktycznie wjechała do buildu
docker-compose build --build-arg NEXT_PUBLIC_BASE_URL=http://localhost:8080

GitHub Actions — co się dzieje po git push

# 1. job "build" na GitHubie
docker login ...
docker build -f Dockerfile -t sebastiankociuba/node-frontend:latest .
docker push sebastiankociuba/node-frontend:latest

# 2. job "deploy" — kopiuje plik, potem po SSH:
docker rm -f $(docker ps -aq --filter publish=3002) || true
docker-compose down || true
docker-compose pull
docker-compose up -d
docker image prune -f

Ręcznie na serwerze — debugowanie

# wejdź na VPS i sprawdź co żyje
ssh user@serwer
cd /var/www/frontend-node

docker ps                        # czy kontener VPS-2-FE działa
docker logs -f VPS-2-FE          # logi na żywo
docker-compose config            # jaki obraz/porty faktycznie zostaną użyte
docker-compose pull && docker-compose up -d   # ręczny redeploy bez CI

Kto tworzy obraz?

Wyłącznie GitHub Actions, wg przepisu z Dockerfile. Serwer nigdy nie buduje.

Kto uruchamia kontener?

Wyłącznie serwer, wg instrukcji z docker-compose.yml. GitHub nigdy nie odpala kontenera produkcyjnego.
